## E-mail rendering, delivery log and the test-data resets
- Defect found from a real Gmail message: the developer's monthly revenue summary arrived as a wall of base64. `MailService::multipart()` built each MIME part's `Content-Type` and `Content-Transfer-Encoding` lines from single-quoted PHP strings, so the four characters `\r\n` went on the wire instead of a line break, no part ever had a blank line ending its header block, and the client read the whole part as header noise. Every automated message was affected — student OTPs and welcomes, HR and developer copies, payment decisions, certificates — not only the developer summary.
- Fixed by building both alternatives through one closure that uses real `"\r\n"` line breaks, then verified on the wire: a loopback SMTP capture of the six `MailService` send methods — developer revenue report, new-student alert, OTP, payment submitted, payment decision, certificate issued — which fan out into eleven messages across the student, HR, developer and approving-admin mailboxes, and every one of them reports two correctly separated parts, a closing boundary, a clean strict-mode base64 decode and a body that round-trips byte for byte.
- `tests/auth-flow-smoke.php` now parses the captured bytes the way a mail client does — split on the boundary, headers separated from payload, `base64_decode(..., true)`, literal-`\r\n` leak check — and fails with *"Registration delivered a message a mail client cannot render"*. Proven as a regression guard: with the committed `MailService` restored the run fails, with the fix it passes.
- `tests/email-notification-smoke.php` adds a socket-free envelope check that calls the private `multipart()` through reflection and asserts real CRLFs, exactly two alternatives, exact header lines and a decode that returns the original text including a non-ASCII word.
- `tests/purge-tools-smoke.php` drives two more endpoints in child processes: `POST /admin/students/purge` (mistyped phrase deletes nothing; the right phrase removes the account with its enrolment, attendance, submission with its stored file, payment, certificate, grade, OTP, sign-in events and audit rows, keeps the course, the assignment, the admin and the announcement, unlinks rather than deletes the delivery-log row, retires the payment notification and audits `student.bulk_deleted`; an empty directory says so) and `POST /admin/announcements/email-log/clear` (a request without a valid CSRF token empties nothing, a valid one clears the rows and audits `email_log.cleared`, and an already empty log reports it).
- `tests/interface-render-smoke.php` renders the student directory and asserts its *Delete all students* card, and asserts the announcement workspace carries the *Clear activity* control.
- Mobile layout measured, not assumed: the announcement workspace was rendered from the development database and loaded in a browser frame at 390, 360 and 320 px. The document scroll width equals the viewport at all three, no element crosses the right edge and no container scrolls sideways; each delivery-log row shows every column as its own labelled line and the *Clear activity* button wraps under the card heading instead of squeezing it.
- Not tested: a real Gmail round trip. Everything above is verified against a loopback SMTP server, so the client-side rendering proof is the parser's, not Google's; and the two new destructive tools have not been clicked through in a logged-in browser session.

## Schema re-import and harness isolation
- Reported from phpMyAdmin: importing the schema file into a database that already carries IDs failed with `#1062 Duplicate entry 'TSG-ADM-00001' for key 'uq_users_account_reference'` and stopped there, leaving the statements after it (the student counter bump, the retired-setting cleanup) unrun. Cause: the admin backfill numbered accounts with no ID from `00001` regardless of what was already handed out, so any database holding one filled admin and one empty-ID admin could not be re-imported.
- Reproduced and fixed in a scratch database (`tsg_schema_check_tmp`, dropped afterwards): seeded with an admin at `TSG-ADM-00001`, an admin with no ID, a student at the legacy `TSG-SMOKE-700`, a student with no ID and the counter behind at `1`. The committed file fails exactly as reported and leaves the second admin at `NULL`; the fixed file imports cleanly to `TSG-ADM-00002` and `TSG-CER-701` and moves the counter to `702`; a third import changes nothing, which is the idempotence the single-schema-file convention depends on.
- Root cause of the polluted development database that triggered it: `interface-render-smoke.php`, `certificate-verify-smoke.php` and `admin-identity-flow-smoke.php` checked the scratch-database name with the same soft `$assert` the rest of their checks use, so pointing one at `tsg_academy_lms` recorded a failure and then ran the whole suite anyway — seeding fixture admins, students, courses and notifications into the live database. All three now print the refusal to stderr and `exit(1)` before any connection; verified by running each with no `--database=` and seeing only the refusal line.
- Not cleaned automatically: the fixture rows an earlier run left in the development database (`render-smoke-admin@example.test`, `render-smoke-student@example.test` with their course and notifications) are the admin-with-no-ID that made the import fail, and removing accounts is left as a deliberate decision rather than a test's side effect.

## Course-first enrolment checkout
- Reported from manual testing: a visitor who bought nothing could still open an account from the sign-in page's *Create an account* link, meet an empty dashboard, and walk back through the catalogue to reach the payment form — the same trip they had just come from. The diagnosis was half right and the half that was wrong mattered. The loop is real, and its cause is that nothing anywhere carried the chosen course: there was no `_intent`, `redirect_to` or `next` in `app/` at all, and `AuthController::login()` always redirected to `/dashboard`, so the course was lost at the first click. What is *not* true is that the open registration let anyone into paid content — `LearningController` requires a live `student_course_access` row and `AuthMiddleware::requireRole` requires `status='active' AND email_verified_at IS NOT NULL`, and both were verified before any change was made. The fix was therefore a journey fix, not an authorisation fix, and no gate was loosened.
- The journey is now `Enroll now` on a course page → `GET /enrol/{slug}` → account step → code step in the same card → verified, signed in and delivered to `/payments/new?course_id=…` for that course. `tests/enrol-flow-smoke.php` drives it over real HTTP against a scratch database (`tsg_enrol_check_tmp`, imported and dropped by the run itself, name-guarded with `exit(1)` before any connection) with `php -S` on a loopback port and cookie jars, so the redirects, the session and the rendered card are checked as a browser meets them.
- Proven by that harness: the five routes and the card's JS hooks exist; the card posts no course id at all, and a forged `course_id` in the body cannot move the verified hand-off, which reads the session only; unknown, unpublished and zero-priced slugs each bounce to the catalogue *with a notice that renders and is then cleared* — a leak found while writing it, because `/courses` had no reader for `_flash_error` and the message would have reappeared on the next page; `GET /register` is a redirect, not a door; the code step arrives in the same card and still names the course; a wrong code re-renders, leaves the account pending and leaves the issued code unconsumed, so one typo does not cost a new OTP; confirming activates the account, signs it in and opens the existing bank-details page with the upload and reference fields untouched; a course unpublished between two steps drops the student back to the catalogue and the same link works again once it is back; signing in with an intent goes to the course and without one goes to the dashboard, as before; a forged CSRF token on either step answers 419 and creates no account.
- The resend wait is now its own setting (`otp_resend_cooldown_seconds`), and the discriminating check lives where the numbers can be controlled: `enrol-flow-smoke.php` writes a 600-second lifetime against a 40-second cooldown and asserts the card hands the browser 40, which is the only way to prove the countdown reads the cooldown rather than the expiry. `auth-flow-smoke.php` runs on the development database, where an admin's own values decide both numbers, so it asserts only that the row is seeded and that the countdown never exceeds it — an earlier version demanded the cooldown be strictly below the lifetime, which is a preference, not an invariant, and failed on a database where the admin had set both to 60.
- Importing the schema is required for the new setting to exist; on the development database the import added exactly one row (`otp_resend_cooldown_seconds = 60`) and left every stored value and every account byte-identical, checked by diffing the full `app_settings` table and the row counts of users, courses, payments, notifications, delivery log, access grants and certificates before and after. The admin's `otp_lifetime_seconds = 60` and their payment account details survived, which is what the file's `ON DUPLICATE KEY UPDATE setting_key = VALUES(setting_key)` no-op is for.
- `AuthService::register()` returning two flags instead of one boolean was absorbed by `auth-flow-smoke.php` (both call sites assert the exact array). `email-notification-smoke.php` and `admin-identity-flow-smoke.php` turned out not to call `register()` at all, so the shape change needed nothing there; `interface-render-smoke.php` gained the catalogue-CTA-by-role checks and keeps its existing fixture assertions.
- Not tested: the card has not been walked through in a browser, so the in-flight progress panel, the countdown ticking down visually and the *Wrong email? Go back* control are proven in HTML and JavaScript source and through HTTP, not on screen; the new `pages.css` blocks have not been measured at 390/360/320 px the way the announcement workspace was; and the mail timing is still loopback, so a real mailbox's delay — the case this whole UX fix is about — is not reproduced here.

## Required before quiz release
- Deadline enforced on server even if client clock is changed.
- Student cannot submit another student's attempt.
- Correct answer key never appears in the student question payload.
- Attempt can be finalized only once; duplicate requests do not duplicate scoring.
- Hidden-tab/focus event records the policy reason; server rejects invalid attempt states.
- 75 questions × 4 options are supported; scoring for all-correct, all-wrong, unanswered and mixed responses is verified.
- Pass/fail boundary and rounding rules are explicit and tested.

## Required before announcements/reports release
- Student can only read/reply to notifications addressed to them.
- Admin can see reply author, body and timestamp.
- Unread count changes after opening a notification.
- Weekly/monthly report totals reconcile with underlying quiz and assignment records and use the configured timezone.
